Next.js는 별도의 설정 없이 폴더와 파일의 구조를 기반으로 URL 경로를 자동 생성하는 파일 시스템 기반 라우팅(File-based Routing) 방식을 사용한다.

### 라우팅 방식
Next.js에는 라우팅 방식이 두가지가 있다고 한다.
#### 1. Pages Router
- Next.js 원조 라우팅 방식으로 파일 하나가 곧 라우트.
- 예시) pages/posts/[slug].js

> 여기서 **slug는** ? 
웹페이지나 게시물의 고유 주소(URL)에서 가독성을 높이기 위해 핵심 의미만 담아 텍스트로 표현한 것으로 SEO(검색엔진 최적화)에 사용하기 좋다.


- 서버에서 데이터 페칭을 해야할 때는 getStaticProps / getServerSideProps 와 같은 별도 함수로 진행해야한다.



#### 2. App Router
- 폴더가 라우트 세그먼트로 그 안의 page.tsx가 실제 UI.
- React Server Components가 기본값으로, 컴포넌트가 서버에서 렌더링되고, fetch나 DB호출처럼 데이터를 컴포넌트 안에서 직접 가져가 쓸 수 있다.
- layout.tsx, not-found.tsx, loading.tsx, error.tsx 같은 특수 파일들로 공통 UI/에외 상황을 처리할 수 있다.

는.. 사실 AI가 알려준 것만 봤을 때 뭐가 다른 건지 잘 와닿지가 않았다. 🫠 하핳
파일 기반 라우팅이라는 것 자체는 같아서 같은 원리가 아닌가 싶었기 때문ㅠ 


그래서 둘의 차이점을 찾아가면서 이해해보기로 했다.

### 둘의 차이점
#### 1. 레이아웃의 구조
Pages Router는 앱 전체를 감싸는 `_app.js` 하나만 있다. App Router는 `app/layout.tsx(전체)` 뿐만이 아니라 `app/posts/layout.tsx` 특정 경로 밑에만 적용되는 레이아웃을 중첩해서 쓸 수 있다. 

```ts
_app.js
  └─ <Component {...pageProps} /> ← 여기에 현재 페이지 컴포넌트가 통째로 들어감
```
Pages Router는 하나의 틀에 페이지를 통째로 갈아끼우는 구조로, `_app.js` 자체를 변경하기 때문에 바뀌는 것을 구분할 구조적 단위 자체가 없다. URL이 파일 하나에 1:1로 매핑되기 때문이다. 


```ts
app/layout.tsx           ← "/" 이하 전부
  └─ app/posts/layout.tsx  ← "/posts" 이하 전부 (있다고 가정)
       └─ app/posts/[slug]/page.tsx  ← "/posts/1", "/posts/2" ...
```
여기선 URL `/posts/123`이 `/ `→ `/posts` → `/posts/123`, 이렇게 세그먼트별로 쪼개져서 각 폴더의 `layout.tsx`가 그 세그먼트를 감싸는 트리 구조를 이룬다. `/posts/1`에서 `/posts/2`로 이동하면, Next.js는 "어? `/`랑 `/posts` 구간은 URL이 안 바뀌고, 바뀐 건 [slug] 부분뿐이네"라고 판단해서, 그 바뀐 부분만 React 트리에서 교체하고 나머지(layout.tsx들)는 그 자리에 그대로 둔다.

요 부분을 확인하다보니 `React` 자체의 diff 알고리즘이 생각났다. `React`는 트리에서 같은 자리에 같은 컴포넌트가 일부만 바뀌면 트리 일부만 바뀌는 원리니까! 

#### 2. 데이터 페칭

**Pages Router**는 데이터를 가져오는 방법이 정해진 이름의 함수로 따로 있다.
- `getServerSideProps`: 매 요청마다 서버에서 실행 (요청 시점 데이터가 필요할 때)
- `getStaticProps`: 빌드 타임에 미리 실행해서 정적으로 생성 (SSG) 할 수 있다. `revalidate` 옵션으로 일정 주기로 재생성(ISR)도 가능하다.

여기서 중요한 건, 이 두 함수가 **컴포넌트 함수랑 완전히 분리된, 이름이 정해진 독립 함수**라는 점이다. "이 페이지가 어떤 데이터를 필요로 하는지"를 Next.js가 알아보려면, 저 이름(`getServerSideProps`, `getStaticProps`)으로 약속이 돼 있어야 한다. 반환값도 `{ props: {...} }` 형태로 맞춰줘야 하고, JSON으로 직렬화 가능한 값만 넘길 수 있다. (예를 들어 `Date` 객체는 그대로 못 넘기고 문자열로 바꿔줘야 한다.)


**App Router**는 이런 별도 함수가 아예 필요 없다. Server Component 함수 본문 안에서 그냥 `await fetch(...)`를 쓰면 끝이다.
```ts
// 서버컴포넌트
export default async function Page() {
  const data = await getData();
 
  return <main>{/* ... */}</main>;
}

``` 
RSC(React Server Component) 지원으로 Pages Router의 `getServerSideProps`, `getStaticProps`를 사용하지 않고 컴포넌트에서 바로 fetch API를 사용하여 바로 데이터를 페칭할 수 있다.

정리하면, Pages Router는 "데이터 가져오기"랑 "화면 그리기"가 언어적으로 분리된 두 함수였는데, App Router에서는 하나의 함수 흐름 안에 자연스럽게 녹아있다. 레이아웃 구조에서 "통짜 교체 vs 트리 구조"로 나뉘었던 것처럼, 데이터 페칭에서도 결국 같은 방향성으로, 분리해서 프레임워크와 약속하는 방식 vs 하나의 흐름으로 자연스럽게 처리하는 방식으로 나뉘는 셈이다.


### 요 블로그는 App Router 방식을 선택했다. 👏👏👏

처음에 Next.js를 선택한 이유 자체가 SSR을 살리고 싶어서였는데, App Router가 바로 그 목적에 제일 자연스럽게 맞물리는 방식이었다. Server Components가 기본값이라는 것 자체가 "서버에서 렌더링한다"는 걸 억지로 설정하는 게 아니라, 그냥 기본으로 깔려있는 셈이니까. 
(그리고 사실 App Router를 자연스럽게 많이 쓰는 추세이기도 하고 ㅎㅎ)

실제로 지금까지 설명한 개념들이 프로젝트 곳곳에 그대로 녹아있다.

- **동적 라우트 + `notFound()`**: `app/posts/[slug]/page.tsx`에서 slug에 해당하는 글이 없거나 비공개(`published: false`)면 `notFound()`를 호출해서 404로 떨어뜨리는 구조를 만들었다.
- **특수 파일 `not-found.tsx`**: 저 404 화면을 커스텀하려고 `not-found.tsx` 파일을 만들었는데, 처음에 `not-foud.tsx`로 오타를 내서 한참 "왜 안 먹히지?" 했었다. 😇  칼같은 Next.js.. (당연)
- **`searchParams`로 상태 관리**: 서버 컴포넌트는 애초에 훅을 못 쓰니까 태그 필터(`?tag=`)랑 페이지네이션(`?page=`)을 `useState` 없이 URL 쿼리로 처리했다.
- **Server Component라서 가능했던 것**: `import { posts } from "@/.velite"`를 컴포넌트 안에서 바로 썼다. Pages Router였으면 이 데이터 처리 로직을 `getServerSideProps` 안에 억지로 분리해야 했을 텐데, App Router는 그냥 자연스럽게 한 함수 안에서 처리하게 해준다.


### 결론

처음엔 "파일이 URL 되는 거 둘 다 똑같은 거 아니야?"라고 생각했는데, 파보니까 포장지만 같고 속은 완전히 다른 아키텍처였다. Pages Router는 페이지 하나를 통째로 갈아 끼우는 구조고, App Router는 URL 경로 자체가 컴포넌트 트리 구조를 이루는 방식이었다. 이 차이가 레이아웃 중첩이나 데이터 페칭 방식 전부를 결정하고 있었다.

다음엔 Server Component/Client Component 경계(`"use client"`)를 더 깊게 파보거나, 이번에 같이 알게 된 Router Cache 이슈를 직접 재현해보는 글을 써볼까 한다. (미래의 내가 하겠지 🙃)
